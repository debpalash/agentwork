# Collagent product and UI audit 001

Date: 2026-08-28

Status: FAIL. This interface is a promising technical alpha, not an adoption-ready product.

Scope: product positioning, role design, core user journeys, React architecture, TypeScript enforcement, accessibility, responsive behavior, failure states, content integrity, visual system, and public documentation.

Method: source inspection, live route checks across 11 routes, a 390 px viewport pass, keyboard and semantic checks, simulated API failure, contrast calculations, TypeScript configuration inspection, and a production build. The named Matt Pocock skill is not installed, so the React and TypeScript portion applies the same strictness directly: make invalid states difficult to represent, keep async state explicit, and make the compiler and tests prove useful things.

## Executive scorecard

| Lens | Score | Verdict |
| --- | ---: | --- |
| Product thesis | 8/10 | The open problem protocol is meaningful and technically more substantial than the visible UI suggests. |
| Closed-loop usefulness | 3/10 | The public interface cannot complete most of the problem lifecycle it markets. |
| Adoption readiness | 3/10 | Roles, onboarding, data provenance, and terminology block builders and funders. |
| Visual polish | 6/10 | The brand mark and dark palette are coherent, but the interface relies on a generic terminal costume. |
| UX clarity | 3/10 | Users must decode protocol jargon and conflicting product models before they can act. |
| Accessibility | 2/10 | Keyboard, focus, labels, contrast, and touch target requirements fail. |
| React and TypeScript rigor | 3/10 | The stack is modern, but type safety, error containment, server-state handling, tests, and route splitting are not. |

CEO verdict: do not market this as a world-scale collaboration network yet. Market it as an open protocol alpha with an executable code-task wedge, then close one complete funder-to-contributor-to-verifier loop.

CTO verdict: the backend protocol work has merit. The frontend currently weakens trust in it by hiding failures, presenting seed state as live state, and providing little compile-time or test protection.

## Findings

### 01. The central promise is not a usable closed loop

Priority: HIGH. Rules: R-26, R-38. Reason: the landing page promises funding, decomposition, contribution, evidence, review, credit, and reward, but the problem interface only publishes a charter and reads a graph.

Evidence:

- The promise is stated in `frontend/src/pages/Landing.jsx:67-68` and `frontend/src/pages/Landing.jsx:136-139`.
- `frontend/src/pages/Problems.jsx:91-188` has create, filter, and inspect behavior only. It has no funding action, workstream creation, contribution submission, evidence attachment, review, reward, or credit action.
- The API already exposes workstream, contribution, evidence, and review endpoints in `server/src/routes/problems.ts:419-640`, so the visible product is behind the protocol.

Recommendation: choose and ship one complete public loop. The recommended loop is: funder drafts and funds a charter, contributor joins one workstream, reviewer accepts or rejects evidence, and both parties see the resulting credit and payment state.

### 02. The product has no coherent role model

Priority: HIGH. Rules: R-24, R-37. Reason: navigation and page hierarchy cannot be correct until funder, builder, agent, reviewer, institution, and operator responsibilities are explicit.

Evidence:

- The dashboard still frames Collagent as an autonomous labor marketplace in `frontend/src/pages/Dashboard.jsx:62-75`.
- The task form tells an unregistered funder to register an agent before posting in `frontend/src/pages/PostTask.jsx:179-189`.
- The agent directory says any agent can both post and bid in `frontend/src/pages/Agents.jsx:80-83`.
- The navbar labels every role with one technical vocabulary in `frontend/src/components/Navbar.jsx:30-38`.
- No `DESIGN.md` or equivalent product-role direction exists.

Recommendation: make the human decision model explicit. Funders open and fund work, builders and agents find and perform work, reviewers verify it, institutions govern high-risk work, and operators administer the network. Do not make a sponsor impersonate an agent.

### 03. Seeded state is presented as live network evidence

Priority: HIGH. Rules: R-17, R-38. Reason: an evidence product cannot leave users guessing whether activity, balances, jobs, and identities are production, testnet, or demo data.

Evidence:

- The landing feed is labelled live in `frontend/src/pages/Landing.jsx:90-105`.
- The marketplace says displayed results come from indexed platform state in `frontend/src/pages/Landing.jsx:176-183`.
- The running API returned six jobs created by `scripts/seed.js:93-132` and repeated synthetic problem events from test wallets.
- The UI shows `BASE_L2` even when the configured chain is local Hardhat, through `frontend/src/components/Navbar.jsx:121-123`.

Recommendation: add a persistent environment and provenance banner: Local demo, Base Sepolia testnet, or Base mainnet. Label seeded records as demo data and never mix them with adoption metrics.

### 04. Network failure is rendered as legitimate zero or empty data

Priority: HIGH. Rules: R-17, R-27, R-38. Reason: users receive false business information when transport failure looks identical to an empty network.

Evidence:

- `apiFetch` converts every GET failure to `null` in `frontend/src/api.js:37-65`.
- `fetchStats` converts that failure to real-looking zeros in `frontend/src/api.js:69-80`.
- With `/api/*` blocked in the browser, the landing page still rendered LIVE with four zero metrics, the dashboard rendered zero metrics and an empty queue, and tasks, agents, and problems rendered their normal empty states. None rendered an error or retry action.
- The SSE connection closes permanently on its first error in `frontend/src/api.js:123-133`.

Recommendation: use a typed result or thrown error, let React Query own retries and cache state, and render separate first-run, filtered-empty, offline, unauthorized, and server-error states.

### 05. The footer ships dead controls

Priority: HIGH. Rules: R-24, R-26, R-38. Reason: visible navigation claims integrations and community destinations that do not exist.

Evidence:

- MCP Server and Discord both use `href="#"` in `frontend/src/App.jsx:34-39`.
- An unused alternative footer contains eight more dead links in `frontend/src/components/Footer.jsx:14-28`.

Recommendation: link real destinations, visibly mark an honest coming-soon item, or remove it. Delete the unused footer after confirming it has no intended role.

### 06. Four important mobile screens overflow horizontally

Priority: HIGH. Rules: R-03, R-35. Reason: users lose content and controls on the primary mobile breakpoint.

Evidence from a 390 px browser viewport:

- Dashboard document width: 622 px.
- Agent directory document width: 802 px.
- Bid interface document width: 511 px.
- Task details document width: 582 px.
- `body { overflow-x: hidden; }` at `frontend/src/index.css:49-62` masks some overflow instead of fixing it.
- Agent rows retain `200px 1fr auto` at `frontend/src/index.css:305-318` with no mobile reflow.
- Bid and detail layouts use fixed inline grid structures without mobile variants.

Recommendation: reflow these views at their content breakpoints, add `min-width: 0` where grid children need to shrink, replace desktop rows with mobile summaries, and verify zero page-level horizontal overflow at 320, 375, 390, 768, and 1024 px.

### 07. Most touch targets are below the 44 px minimum

Priority: HIGH. Rules: R-03, R-35. Reason: the core navigation and filters are difficult to operate reliably with a thumb.

Evidence from live computed sizes:

- Mobile home mark: 34 by 34 px.
- Mobile menu: 38 by 38 px.
- Connect button: 135 by 26 px.
- Task and agent filters: typically 47 to 90 px wide by 24 px high.
- Documentation tabs: 35 to 39 px high.
- The small button style is only `4px 12px` in `frontend/src/index.css:192`.

Recommendation: separate visual size from hit area and make every interactive target at least 44 by 44 px with sufficient spacing.

### 08. Mouse-only cards and missing focus treatment block keyboard users

Priority: HIGH. Rule: R-32. Reason: essential discovery and selection actions cannot be reached or understood without a pointer.

Evidence:

- Task cards are clickable `div` elements in `frontend/src/pages/TaskBoard.jsx:87-123` and `frontend/src/pages/Dashboard.jsx:145-159`.
- Landing task rows are clickable `div` elements in `frontend/src/pages/Landing.jsx:184-200`.
- Problem cards support Enter but not Space in `frontend/src/pages/Problems.jsx:177-183`.
- The chain switch control is a clickable `div` in `frontend/src/components/Navbar.jsx:112-123`.
- Form controls remove the browser outline at `frontend/src/index.css:334-338`, and there is no global `:focus-visible` replacement.

Recommendation: use links for navigation, buttons for actions, native controls for toggles, Space and Enter where a custom button is unavoidable, and a consistent high-contrast `:focus-visible` ring.

### 09. Forms have labels visually, but not programmatically

Priority: HIGH. Rules: R-27, R-32. Reason: screen readers cannot associate fields with their labels, and users do not receive actionable validation feedback.

Evidence from live checks:

- The post-task form exposed 12 visible fields with no associated label.
- The live bid form exposed one unlabeled amount field.
- The open-dispute form exposed two unlabeled fields.
- The problem filter is unlabeled, and the hidden charter form repeats the same detached-label pattern in `frontend/src/pages/Problems.jsx:136-163`.
- Forms rely on native constraints or a single result box instead of field errors, an error summary, focus movement, and `aria-live` status.

Recommendation: give every field a stable `id` and `name`, bind `htmlFor`, add autocomplete where applicable, validate per field, focus the first error, and announce submit state and outcomes.

### 10. Small low-contrast text fails WCAG AA

Priority: HIGH. Rule: R-25. Reason: a frequently used text token is below the 4.5:1 normal-text threshold on every shipped surface.

Evidence:

- `--text-ghost` is `#58716d` in `frontend/src/index.css:30-35`.
- Its contrast is 3.67:1 on `#061012`, 3.48:1 on `#091719`, and 3.30:1 on `#0c1d20`.
- It is used as text as small as 0.55 to 0.75 rem in the brand descriptor, documentation, and landing metadata.

Recommendation: raise the token to a tested AA color, reserve sub-AA decorative tones for non-text only, and add automated contrast checks for tokens and component states.

### 11. Ten undefined design tokens silently invalidate styles

Priority: HIGH. Rule: R-35. Reason: entire declarations disappear at runtime, so several screens do not use the colors, borders, fonts, and surfaces their code appears to specify.

Evidence:

- Undefined tokens: `accent-amber`, `accent-cyan`, `accent-green`, `accent-purple`, `bg`, `bg-mid`, `border`, `font-bold`, `surface`, and `text-primary`.
- They appear throughout `frontend/src/pages/Disputes.jsx:127-399`, `frontend/src/pages/Docs.jsx:505-516`, `frontend/src/pages/BidArena.jsx:127-234`, and `frontend/src/pages/TaskDetails.jsx:72-156`.
- The root token list at `frontend/src/index.css:8-44` defines different names.

Recommendation: create one typed token contract, migrate every consumer to it, and add a build-time check that fails on undefined custom properties.

### 12. React has no dependable crash or async containment strategy

Priority: HIGH. Rules: R-27, R-35. Reason: one rejected promise or malformed response can replace the product with a generic router failure or leave stale state behind.

Evidence:

- `frontend/src/App.jsx:23-80` defines no route error component, not-found component, or application error boundary.
- Most data pages use manual `useEffect` fetching even though React Query is installed and provided globally.
- Wallet provider event listeners are registered without cleanup in `frontend/src/context/Web3Context.jsx:27-47`.
- `connectWallet` does not await `handleConnect` in `frontend/src/context/Web3Context.jsx:77-87`.
- Effects in landing, dashboard, task board, agents, profile, and post task do not consistently cancel stale work.

Recommendation: add route-level and application-level error boundaries, standardize server state on React Query, type and validate API responses, and make every effect return the cleanup it owns.

### 13. The TypeScript configuration is safety theater

Priority: HIGH. Rule: R-35. Reason: CI reports a successful frontend build while the compiler and tests prove almost nothing about the UI.

Evidence:

- All frontend source is JavaScript or JSX. There are no TS or TSX source files.
- `frontend/tsconfig.json` enables `strict` and `allowJs` but not `checkJs`.
- `tsc --showConfig` includes generated `dist` JavaScript because the project has no `include` or `exclude` boundary.
- `typescript` is a peer dependency, not a dev dependency, in `frontend/package.json:18-20`.
- The frontend has no test, lint, or typecheck scripts. CI only runs `bun run build` at `.github/workflows/ci.yml:117-132`.

Recommendation: migrate boundary-first to TSX, starting with API result types, route search schemas, Web3 context, and form models. Add typecheck, lint, unit, component, accessibility, and route smoke-test jobs to CI.

### 14. The frontend ships a monolithic route bundle

Priority: HIGH. Rule: R-35. Reason: the production build warns before real adoption traffic exists, and every user downloads pages they may never open.

Evidence:

- Every page is eagerly imported in `frontend/src/App.jsx:6-16`.
- The production build emitted a 710.50 kB minified JavaScript entry, 212.31 kB gzip, and Vite's chunk-size warning.
- The TanStack router Vite plugin is installed but not configured in `frontend/vite.config.js:1-15`.

Recommendation: lazy-load route components, separate wallet and contract code from public discovery routes, configure route splitting, and track bundle budgets in CI.

### 15. No written design direction exists

Priority: HIGH. Rule: R-37. Reason: the palette, typography, spacing, terminal voice, fixed dark theme, dot grid, card system, and motion have no durable product rationale.

Evidence:

- No `DESIGN.md` exists.
- Comments such as "Campaign-derived foundation" and "premium dark aesthetic" in `frontend/src/index.css:8-44` and `frontend/src/index.css:645-647` describe style, not audience, purpose, or decision rules.
- ENERGY, RHYTHM, and MOTION dials are not declared.

Recommendation: before visual fixes, write the design direction around trust, evidence, plural participation, and high-stakes legibility. Record one-line reasons for palette, typography, density, motif, motion, and theme.

### 16. The visual system defaults to terminal aesthetics without a product reason

Priority: MEDIUM. Rules: R-01, R-06, R-07. Reason: neon accents, radial glow, dot grid, JetBrains Mono, bracket labels, underscores, and fake system messages are used as a generic signal for technical credibility.

Evidence:

- The global background combines two radial gradients with a repeating dot grid in `frontend/src/index.css:49-57`.
- The landing hero contains a fake terminal with traffic-light dots in `frontend/src/pages/Landing.jsx:90-107`.
- Monospace, uppercase, brackets, command fragments, and machine metaphors dominate funder and reviewer flows.

Recommendation: show the real evidence graph or a real workstream view in the hero. Keep monospace for identifiers, hashes, code, and machine-readable state. Use plain human language everywhere else.

### 17. Iconography is inconsistent and frequently decorative

Priority: MEDIUM. Rule: R-04. Reason: emoji and unrelated glyphs add visual noise while changing by operating system and providing weak semantic meaning.

Evidence:

- Emoji status markers appear in `frontend/src/pages/TaskBoard.jsx:4-20`.
- Activity emoji appear in `frontend/src/pages/Landing.jsx:28-29` and `frontend/src/pages/Landing.jsx:98-104`.
- Documentation and dispute screens mix emoji, mathematical glyphs, and custom outline icons.

Recommendation: use one restrained icon system for navigation and actions, use text plus color-independent state indicators for status, and remove decorative glyphs that carry no information.

### 18. Motion is ungoverned and does not respect user preference

Priority: MEDIUM. Rule: R-19. Reason: looping and counting effects run without a declared purpose or reduced-motion fallback.

Evidence:

- The chain indicator blinks forever at `frontend/src/index.css:137`.
- Landing counters run timed intervals in `frontend/src/pages/Landing.jsx:6-24`; the interval itself is not cleared by effect cleanup.
- No `prefers-reduced-motion` rule exists.

Recommendation: declare the motion dial, stop decorative loops, clear all timers, and provide a reduced-motion mode that removes nonessential animation.

### 19. Copy and information architecture make users decode the product

Priority: LOW. Rules: R-05, R-15, R-16, R-20. Reason: technical theater displaces the role, action, consequence, and trust information a first-time user needs.

Evidence:

- Navigation uses `mission_control`, `operations_queue`, `neural_directory`, and `deploy_task` in `frontend/src/components/Navbar.jsx:30-38`.
- Pages use phrases such as swarm bidding, neural node, matrix, thread, and code over meatspace.
- `Explore Contributors` is a generic CTA in `frontend/src/pages/Landing.jsx:279-281`.
- `Trustless payments on-chain` in `frontend/src/pages/Dashboard.jsx:66-68` is an absolute security claim that should not ship without independent evidence.

Recommendation: use task language tied to roles: Fund a Problem, Find Work, Submit Evidence, Review Results, Manage Funding, and Read Protocol Docs. State guarantees precisely and link to the mechanism or audit evidence.

### 20. The rebrand is externally split between Collagent and AIWork

Priority: LOW. Rules: R-20, R-31. Reason: builders cannot tell which names are current product surfaces and which are deliberate compatibility identifiers.

Evidence:

- The repository contains 384 case-insensitive AIWork references and 118 Collagent references outside installed dependencies and build output.
- Public packages remain `@aiwork/sdk`, `@aiwork/cli`, and `@aiwork/agent-runner`.
- The documentation uses Collagent classes with legacy package names and ad hoc comments in `frontend/src/pages/Landing.jsx:221-225` and `frontend/src/pages/Docs.jsx:42-49`.
- CI is still named AIWork at `.github/workflows/ci.yml:1`.

Recommendation: write a compatibility and migration policy before renaming protocol identifiers. Present one public brand, clearly label legacy package and signing namespaces, and publish the future namespace plan.
